## How to read an epic file

Each epic file has the epic statement, a story table, then one section per story containing:

- the story statement (*As a… I want… so that…*);
- **Implementation** — the frontend and backend files that deliver it;
- **Tests** — automated tests that exercise it;
- an AC table: one *Given / When / Then* scenario per row, with its effort size.

Card writing rules (applied by the revision):

- One Given/When/Then per AC; extra scenarios become extra ACs.
- ACs describe what the shopper sees and presses, in plain words — no API, cache or field names.
- Epics build in numerical order: later epics may reuse earlier features (e.g. Epic 5 schedules unbought items into Epic 4's *Planned items*).
- **Size**: 1–3 small, 3–5 medium, 5–10 large. Story size = sum of its ACs (capped); epic size reflects overall scope.
- **Numbering gaps** (e.g. no US 4.3, 4.7, 5.3, 8.4) are intentional: removed cards keep their numbers retired so references stay unambiguous.

## Keeping this folder current

The epic files, [Retired scope](retired-scope.md) and the [Traceability matrix](../08-evidence/traceability-matrix.md) are generated by [`docs/tools/generate_requirements.py`](../tools/generate_requirements.py) from:

1. a board export of every card (`leankit-sync/live-cards.json` in the project workspace — card text, IDs, assignees, sizes);
2. the applied revision (`us-ac-revision.md` — epic planned windows, and sizes for any card without one);
3. the story → code mapping kept inside the script.

After changing cards on the board, re-export the cards, run the script from the repository root, and review the diff. Update the story → code mapping in the script when a feature moves to new files.
