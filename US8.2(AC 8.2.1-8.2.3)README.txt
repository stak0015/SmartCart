US 8.2 - See what SmartCart saved me (AC 8.2.1-8.2.3)
US 8.2 - 显示 SmartCart 为我省下的钱（AC 8.2.1-8.2.3）

[What this change does / 本次提交内容]

Frontend - calculation layer (steps 1, 2, 3)
- New frontend/lib/savings-insights.ts, a pure module with no React and no
  API calls. It reads only the StoreRecommendation list that Epic 2 already
  returns, so it does not depend on US 5.4 expense records (not yet merged
  into this branch).
- travelSavingsInsight (AC 8.2.1): my store's estimatedRoundTripCostRm minus
  the cheapest reachable alternative's. Stores carrying exceedsLimit are
  excluded from the candidate pool, because they were returned only when
  nothing matched inside the travel limit and recommending one as a saving
  would be unusable for a household that cannot travel that far.
- potentialPriceSavingsInsight (AC 8.2.2): comparison basis is the best
  single store (one trip, achievable), not a per-line theoretical minimum
  spread across several stores. Only basket lines priced at BOTH stores are
  compared, so a line my store has no price for can never read as a saving I
  never had. The result exposes comparableLineCount / basketLineCount so the
  UI can state "based on N comparable items".
- Lines whose price came from the cached cross-store median are counted
  (medianLineCount) and disclosed, following the existing store/median split
  convention in recommendation-detail.ts.
- Both insights return a structured state instead of a bare number:
  available, savingsRm, reason, and the store names. Savings of zero or less
  are reported as unavailable rather than shown as "you saved RM0", which
  would read as a result when no cheaper option exists.
- AC 8.2.3: each insight carries kind: "estimate" | "potential". Route
  metadata (routeProvider, routeWarning) travels with the travel insight, so
  the straight-line fallback cannot be displayed without its caveat.

前端 - 计算层（步骤 1、2、3）
- 新增 frontend/lib/savings-insights.ts，纯函数模块，不含 React、不发
  任何请求。它只读取 Epic 2 已返回的 StoreRecommendation 列表，因此
  不依赖 US 5.4 的消费记录（该代码尚未合并进本分支）。
- travelSavingsInsight（AC 8.2.1）：我的门店 estimatedRoundTripCostRm
  减去最便宜的可达替代门店的同一字段。带 exceedsLimit 的门店被排除在
  候选池之外——这类门店只在出行限制内无匹配时才会返回，把它当作省钱
  推荐给走不到那么远的家庭并不成立。
- potentialPriceSavingsInsight（AC 8.2.2）：比价口径为「最优单店」
  （一次行程、可执行），而非跨多店逐行取理论最低价。只比较两家店
  「都有价格」的购物篮行，因此我的店缺价的商品永远不会被算成我省下
  的钱。结果暴露 comparableLineCount / basketLineCount，供界面说明
  「基于 N 件可比商品」。
- 价格来源为跨店缓存中位价的行会被单独计数（medianLineCount）并披露，
  沿用 recommendation-detail.ts 中既有的 store/median 双源约定。
- 两个洞察都返回结构化状态而非裸数字：available、savingsRm、reason 与
  门店名。省钱额为零或负数时报告为不可用，而不是显示「你省了 RM0」——
  那会在实际没有更便宜选项时被误读为一种结果。
- AC 8.2.3：每个洞察都带 kind："estimate" | "potential"。路线元数据
  （routeProvider、routeWarning）随差旅洞察一起返回，因此直线距离兜底
  不可能在不带警示的情况下被展示。

Frontend - copy and component (steps 5, 6)
- frontend/lib/i18n.ts: 13 new keys in BOTH the English and the Bahasa
  Melayu blocks (AppCopy is inferred from COPY.en, so a missing ms key is a
  compile error). Wording is fixed by the AC: travel savings are always
  "Estimated", price savings are always "Potential", and
  potentialNotActualNote states plainly that potential savings are not money
  already saved.
- New frontend/components/savings-insights.tsx: a stateless summary that
  renders whatever insights it is handed. The estimate/potential badge is
  driven by insight.kind, not chosen by the component, so the wording cannot
  drift from the calculation. Deliberately not wired into any page yet: its
  placement is decided when US 5.4 expense records land, and keeping it in a
  standalone file avoids an "defined but never used" lint warning.

前端 - 文案与组件（步骤 5、6）
- frontend/lib/i18n.ts：英文与马来文两个块各新增 13 个键（AppCopy 类型
  由 COPY.en 推导，缺 ms 键即编译失败）。措辞按 AC 固定：差旅省钱一律
  用 "Estimated"，比价省钱一律用 "Potential"，potentialNotActualNote
  明确写出潜在省钱不等于已经省下的钱。
- 新增 frontend/components/savings-insights.tsx：无状态摘要组件，给它
  数据就渲染。estimate/potential 徽章由 insight.kind 驱动，而非组件自行
  选择措辞，因此文案不会偏离计算结果。本次刻意不接线到任何页面：展示
  位置待 US 5.4 消费记录落地后再定；放在独立文件也避免了「已定义但未
  使用」的 lint 告警。

[Decisions taken from the team discussion / 来自团队讨论的决定]

- Price comparison basis: best single store (option A), not a per-line
  theoretical minimum.
- Partial baskets: compare only lines priced at both stores, and state
  "based on N comparable items" in the UI.
- routeProvider === "straight_line": still show travel savings, but always
  with routeWarning and more conservative wording.
- Placement of the summary: deferred until US 5.4 records land; the
  component is built stateless ("give it data and it renders") meanwhile.
- Build order followed: step 0 -> 1 -> 2 -> 4 -> 3 -> 5 -> 6, with step 7
  (verification) run after each.

- 比价口径：最优单店（方案 A），而非跨店逐行理论最低价。
- 部分购物篮：只比较两家店都有价格的行，并在界面说明「基于 N 件可比商品」。
- routeProvider === "straight_line"：仍显示差旅省钱，但必须带 routeWarning
  且措辞更保守。
- 摘要展示位置：待 US 5.4 记录落地后再定；在此之前组件按无状态方式构建
  （给数据即渲染）。
- 执行顺序：步骤 0 → 1 → 2 → 4 → 3 → 5 → 6，每步之后执行步骤 7（验证）。
